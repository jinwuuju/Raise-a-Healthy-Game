# 콘텐츠 데이터·검수·제작 파이프라인

> **D114 해석:** 공개 주소의 게임은 ‘검수 전 모형’ 표시가 붙은 시제품이다. 아래 ‘공개 manifest에는 approved 이상’은 정식 공개 도감·출시본의 규칙이며, 시제품의 초안 노출은 화면 표시와 빌드 경계 검사(`tools/check_game_build.py`)로 구분한다(D015·D038).

## 원칙

코드는 게임 규칙을, 데이터는 의학 개념과 퀘스트를 소유한다. “새 기관은 파일 하나만 추가하면 된다”는 과장된 목표를 두지 않는다. 기존 조작을 재사용하는 취재는 데이터로 추가할 수 있어야 하며 새로운 생리 상호작용은 새 퍼즐 규칙과 아트 개발이 필요할 수 있다.

의학 내용의 권위는 생성 도구나 게임 점수가 아니라 검증된 출처와 검수 기록에서 온다. AI 초안은 허용할 수 있으나 자동으로 reviewed 상태로 올리지 않는다. 아래 예시는 구조 설계용이며 검수 완료 지식이 아니다.

## 공통 콘텐츠 메타데이터

모든 엔티티는 안정된 id, schemaVersion, contentVersion, locale, title, status, updatedAt, references, review를 가진다. ID는 의미가 유지되는 동안 변경하지 않는다. 삭제 대신 deprecated와 replacementId를 사용한다. quest/region/concept/item/source/asset은 서로 다른 prefix를 쓴다.

상태: draft → source_checked → medical_reviewed → playtested → approved → published. rejected/needs_revision/withdrawn은 별도 보류 상태. 의학 검수와 플레이테스트는 다른 기록이며 서로를 대신할 수 없다. 공개 manifest에는 approved 이상만 들어간다.

## 엔티티별 계약

| 엔티티 | 필수 내용 | 검증할 관계 |
|---|---|---|
| Concept | 정의, 선수개념, 정상 기능, 이상 변화, 관련 질환, 단순화 한계, 흔한 오해 | 선수개념 DAG, 검수 출처 |
| Disease | 이름·관점 태그·주 허브·해부/계통 ID, 정의·원인·병태생리·증상·검사 의미·치료 원리·예방·합병증·흔한 오해·단순화 한계, 판본 있는 기준 수치 | 해부·개념·허브 ID 실재, 정상 개념 선수 관계, 검수 출처 ([질환 아카데미](16-DISEASE-ACADEMY.md)) |
| Quest | 발단, 상태 전이, steps, evidenceRequirements, articleRubric, rewards, repeatPolicy | 개념·맵·보상 ID 실재 |
| Region | mapAsset, spawns, exits, conceptIds, questIds, puzzleDefinitions | 출구 도달 가능·안전 귀환 |
| Evidence | conceptId, actionType, variantId, hintTier, provenance | 해당 과제와 개념 버전 일치 |
| ArticleRubric | 슬롯, 허용 의미 연결, 필수 근거, 금지된 과장, 피드백 | 유효한 해결 경로 존재 |
| Source | 제목, 기관/저자, URL/DOI, 판본, 확인일, 적용 주장, 위치 | 실제 본문과 주장 대응 |
| Review | 검수 역할, 검수자 식별자, 날짜, 버전, 범위, 판정, 수정사항 | 해당 콘텐츠 버전과 일치 |
| Asset | 경로, 제작자, 라이선스, 사용 범위, 출처, 파생 관계 | 배포 권리·파일 존재 |

Concept의 ‘이상 변화’는 없거나 미작성일 수 있다. 입문 설명에 질환을 억지로 끼워 넣지 않는다. review가 null이면 검수되지 않은 것이며 가상의 검수자·검수일을 채우지 않는다.

## 실행용 스키마와 예시의 경계

[data/examples/concept.example.json](../../data/examples/concept.example.json), [quest.example.json](../../data/examples/quest.example.json)은 계약 예시이며 `status: draft`, `runtimeReady: false`다. 현재 의학 근거가 채워져 있지 않으므로 release manifest에 포함될 수 없다. 밸런스 파일도 `design_only`다.

P1은 초기 quest/save 계약을 TypeScript로 만든다. P3은 JSON Schema로 콘텐츠 구조를 고정하고, 스키마에서 타입을 생성하거나 타입과 검증기의 일치 검사를 둔다. 지금 스키마를 만든 척 빈 객체를 검증 통과시키지 않는다.

## 콘텐츠 검증기 필수 규칙

1. 필수 필드·타입·enum·ID 중복·음수 보상 검사.
2. 참조하는 개념·출처·자산·퀘스트의 존재 검사.
3. 선수 지식의 순환 참조와 도달 불가능한 해금 검사. 의도된 순환은 prerequisite가 아닌 relatedConcept로 표현.
4. 필수 퀘스트 경로에서 필요한 골드와 도구가 무료로 제공되는지 검사.
5. 기사 완성 조건과 실제 얻을 수 있는 evidence의 대응 검사.
6. 퍼즐 초기 상태에서 해결 가능한 경로와 접근성 대체 경로 존재 검사.
7. 보상 completionKey 중복과 반복 정책 누락 검사.
8. approved/published 콘텐츠의 출처·검수·권리·단순화 설명 누락을 빌드 실패로 처리.
9. 미번역 키·잘린 긴 문자열·대체 텍스트 누락 검사.
10. 미검수 예시·원본 이미지가 배포 manifest에 섞이면 실패.

현재 `check_design.py`는 설계 파일 일관성만 검사한다. 위의 런타임 콘텐츠 검증기가 구현되었다는 뜻이 아니다.

## 의료 검수 절차

초안 작성자가 주장 단위로 출처와 페이지/절을 연결한다. 의학 검수자는 사실·기전·도해·단순화의 한계를 검토한다. 교육 검토자는 수행 과제가 원하는 개념을 확인하는지 본다. 편집자는 오해를 부르는 제목·대사·결론을 고친다. 게임 QA는 실제 플레이에서 관찰과 설명이 일치하는지 확인한다.

출처 우선순위는 해당 주제의 공신력 있는 교육 자료·전문기관 자료·교과서·관련 연구 원문이다. 검색 결과 요약만 근거로 등록하지 않는다. 지침·치료·역학처럼 변화 가능한 정보는 발행 직전 재확인한다. 개념 출처는 정기 검토하되 내용 변화 신호가 있으면 먼저 검토한다. 기관 홈페이지 링크 하나로 모든 주장을 검수 처리하지 않는다.

검수자 자격과 이해충돌은 프로젝트 내부 기록으로 관리한다. 전문 검수자를 아직 확보하지 못했으므로 **확보 여부는 P0의 열린 결정**이다. 확보 전에는 기전·질환 설명이 포함된 빌드를 의학적으로 검증됐다고 홍보하지 않는다.

## 오류 발견과 변경

오류 신고→영향 콘텐츠 ID·버전 확인→해당 신규 노출 보류→수정·재검수→패키지 버전 증가→저장 호환 확인→변경 내역 공개. 이미 획득한 XP·골드를 회수하지 않는다. 잘못된 개념 증거는 과거 이력으로 보존하고 최신 보충 탐사를 제시한다. 잘못된 기사를 사용자 성적 실패로 돌리지 않는다.

## 콘텐츠 제작 공정과 관리 도구

주제 선정→학습 목표 1~3개→핵심 조작 스케치→선수 지식 확인→의학 근거→회색상자→퀘스트 데이터→검수→플레이테스트→아트·오디오→배포 패키지. 아트부터 대량 제작하지 않는다.

각 취재는 [퀘스트 양식](../templates/QUEST-TEMPLATE.md)으로 작성한다. 비개발자가 JSON 작성에 오래 걸리거나 참조 오류가 반복되면 P4에서 웹 폼 형태의 내부 편집기를 검토한다. 편집기는 승인 상태 변경 이력·검증 미리보기·초안 내보내기부터 만들고 실시간 공동 편집·권한 서버는 실제 필요가 생길 때 추가한다.
