# HUD와 모바일 UX 개발 원칙

2026-10-10 · D033 · 현재 게임과 앞으로 추가할 기능에 적용한다.

## 목적과 현재 문제

플레이어의 중심 행동은 이동→대화/관찰→근거→기사다. 생활 기능은 취재 사이에 선택하는 경험이다. HUD는 지금 어디에 있고 무엇을 하면 되는지 알려주며 월드를 관찰하는 시간을 보호한다.

기존 화면의 문제: 큰 오른쪽 기자 패널과 아래쪽 채팅판이 상시 면적을 차지했고, 저장/파일 관리가 탐험 행동과 같은 우선순위였다. 방향 버튼을 PC와 모바일에 항상 노출했고, 모바일에서는 관리 기능 자체가 숨겨졌다. 현재 목표가 고정되어 장소를 옮겨도 다음 행동을 안내하지 못했다. 버튼 크기·글자·여백·레이아웃 규칙도 통일되지 않았다.

사용자 예시에서 읽은 원칙은 월드 중심, 작은 상태 영역, 접는 목표, 눌러 펼치는 메뉴다. 전투 게임의 전체 버튼 개수나 배치를 이 게임에 그대로 가져오지 않는다. 새 기능을 추가하는 개발 편의가 HUD 노출의 근거가 될 수 없다.

## 근거와 프로젝트 적용

[Apple의 휴대 게임 UI 안내](https://developer.apple.com/videos/play/meet-with-apple/243/)는 터치 화면에서 콘텐츠와 입력이 공간을 공유함을 설명한다. 주요 플레이 영역·안전 영역을 고려하고, 상황에 맞는 입력을 보여주며 탑다운 게임의 탭 이동을 검토하도록 안내한다. 이 프로젝트는 화면 탭 이동과 상황별 조사/대화 버튼을 채택한다.

[Apple Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)는 플랫폼 입력 방식에 맞는 제어와 반응을 설계하는 근거다. [Microsoft XAG107](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/107)은 선호/가능한 입력을 선택할 수 있도록 대체 경로를 제공한다. 화면 화살표는 제거하되 PC 방향키/WASD·E·Esc와 메뉴의 키보드 탐색을 유지한다.

아래 면적/크기는 프로젝트의 검증할 설계 기준이다. Apple의 pt나 Android의 dp를 CSS px와 같은 단위라고 주장하지 않는다.

## 정보와 기능의 계층

| 계층 | 상시 표시 | 펼쳤을 때 | 노출 이유 |
|---|---|---|---|
| 현재 플레이 | 작은 기자 칩·위치·다음 목표 한 가지 | 목표 접기/펼치기 | 방향 파악·진행 맥락 |
| 상황 행동 | 가까운 대상의 조사/대화 버튼 | 해당 대화/주문/관찰 | 지금 실제 할 수 있는 행동 |
| 취재 정보 | 수첩 진입 버튼 | 내 관찰·다음 목표·향후 기사/도감 | 필요할 때 읽기 |
| 관리 | 메뉴 진입 버튼 | 기록/저장·조작 안내 | 플레이 중 빈번하지 않은 기능 |
| 저장 관리 | 기본 HUD에 없음 | 현재 위치 저장·export/import·복구 | 실수 방지·진척 보존 |

상점/집/가구/기관/기사 기능은 실제 구현·해금·관련 상황에 맞춰 이 계층에 넣는다. 빈 슬롯, 작동하지 않는 아이콘, 가짜 알림 점을 수량처럼 늘리지 않는다. 골드와 긴 성장 수치는 기자 정보/구매 화면에서 보여준다. 실제 진단 수치·전투 체력·쿨다운으로 의학 취재를 표현하지 않는다.

메뉴는 메뉴→기록·저장의2단계까지로 시작한다. import는 적용 전에 확인하고 현재 상태를 보관한다. 저장 오류는 숨기지 않는다. 성공 알림은 짧게 보이며 오류는 다음 조치까지 남긴다.

## 레이아웃과 입력 계약

- 월드 캔버스는 전체 뷰포트를 사용한다. 상시 큰 사이드바·채팅판·방향 화살표가 없다.
- 가장 중요한 대상은 플레이어와 관찰할 월드다. 화면 중앙은 인터랙티브 HUD로 덮지 않는다.
- 기자 칩의 외형은 월드/생성 화면과 같은 합성기를 사용한다. 의상 장착은 application의 소유 검증을 거쳐 세 화면에 반영한다. 기자 정보는 칩, 수첩은 HUD에서 직접 열며 메뉴에 중복하지 않는다.
- 문은 걸어서 진입한다. 문/건물 클릭에 즉시 출입을 연결하지 않고 이동 목표만 설정한다.
- 기자 칩은 왼쪽 위, 메뉴/수첩은 오른쪽 위, 목표는 칩 아래의 짧은 접이 영역. **상시 행동 버튼은 두지 않는다(D042).** 사람·사물은 월드에서 직접 눌러 다가가 대화/조사하고, 키보드는 E/Space가 같은 명령을 낸다.
- 가까운 대상은 월드 위의 이름표·말풍선(…)·느낌표로 알린다. 취재 대상은 느낌표, 가까운 사물은 이름표와 삼각 표식을 쓴다.
- 대화창은 화면 어디를 눌러도 다음 줄로 넘어가고 마지막 줄에서 닫힌다. 선택지가 열린 상태에서 바깥을 누르면 ‘그만두기’다. 시트(수첩·메뉴·지도)는 바깥이나 버튼이 아닌 곳을 누르면 닫힌다. 넘기기 탭이 월드 이동으로 새지 않게 한다.
- 모바일 가로/세로에서 같은 기능이 있어야 한다. 작은 화면이라는 이유로 저장 복구를 없애지 않는다.
- 기본 주요 터치 영역48×48 CSS px 이상, 버튼 사이8px를 현재 기준으로 삼는다. 44×44 미만은 명시적 재검토 대상. 작은 그림을 쓸 때도 누르는 영역을 같이 줄이지 않는다.
- safe-area inset을 고려한다. 손가락을 놓는 곳과 읽는 곳을 충돌시키지 않는다. 실제 노치/시스템 제스처 검증은 기기 실측으로 확인한다.
- 본문은 rem 기반으로 확대하며 메뉴/대화는 스크롤 가능하다. 작은 HUD 라벨은 본문을 대신하지 않는다.
- 메뉴를 열면 게임 입력을 잠그고 이동 버퍼를 정리한다. 닫으면 원래 HUD 버튼에 포커스가 돌아간다. 뒤로는 이전 메뉴, 닫기/Esc는 월드 복귀.
- 내부 표현의 픽셀 질감과 DOM 본문 가독성은 분리한다. 본문을 픽셀 저해상도로 깨뜨리지 않는다.

## 앞으로의 작업에서 반드시 확인할 것

새 기능마다 ① 지금 필요한가 ② 어느 상황에서 쓰나 ③ 상시/상황/펼침 중 어디에 두나 ④ 메뉴 깊이는 몇 단계인가 ⑤ 다른 입력으로도 되는가 ⑥ 진척을 잃을 가능성이 있나를 기록한다.

검증은1280×900 데스크톱,390×844 모바일 세로,844×390 모바일 가로를 기본으로 한다. 실제 터치 에뮬레이션으로 탭 이동·메뉴·뒤로·복구를 검사하고 200% 글자, 키보드 전용, 모달 포커스, HUD 겹침, 오류 표시를 확인한다. 큰 버튼을 줄인 것이 접근성 완료의 증거는 아니다.

출시 승인에는 실제 대상 기기와 사람의 플레이가 필요하다. 현재 자동 검사는 그 범위로만 보고한다. UI가 좋아 보인다는 주장 대신 스크린샷·행동 경로·남은 제한을 남긴다.
